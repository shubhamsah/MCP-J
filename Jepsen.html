Jepsen-style testing for MCP and agentic AI

Jepsen breaks distributed databases on purpose. Then it checks if the database kept its promises. This guide applies the same method to MCP servers and AI agents. It explains what such a test proves, what it outputs, what already exists, and how to give a conference talk about it.

How this guide uses Simplified Technical English

ASD-STE100 is a controlled language for technical text. This guide follows most of its rules:

  • Sentences are short: 20 words or fewer for instructions, 25 or fewer for descriptions.
  • Verbs are in the active voice and in simple tenses.
  • Each instruction starts with a verb. Example: "Record the result."
  • One word has one meaning. A fault is always a failure that the test injects. An anomaly is always a wrong result that the checker finds.
  • There are no contractions and very few phrasal verbs.

To keep the text precise, the guide relaxes some rules (the other 20%):

  • It uses technical names that are not in the STE dictionary, for example linearizable, nemesis and idempotent. The glossary defines them.
  • Some explanations use longer sentences with "because" or "if".
  • Code, file names, titles and quotes stay in their original form.

The short answer

Fault injectors and checkers exist. No public tool joins them into the full Jepsen loop for MCP.

An agent that says "paid once" and pays twice is easy to see and easy to remember.
Main risk

Agent runs are random and cost money. Use seeds, cached responses and statistics.
  1. What Jepsen is. Jepsen is a method and a tool to test distributed databases. It sends many operations to a cluster and injects faults. It records a history of all results and checks that history against a formal model. It finds bugs. It cannot prove that there are no bugs.
  2. Does it apply to MCP and agents? Yes. An agent, an MCP client, the network and an MCP server form a distributed system. They have the same problems: lost responses, retries, duplicates and unknown results. In MCP 2026-07-28, a broken response stream loses the request. To get a result, the client must send the request again with a new ID. The protocol has no idempotency key.
  3. What it proves. One counterexample proves a real bug, for example "the agent paid the invoice two times". Many clean runs give only a statistical upper bound. They do not prove that the system is correct.
  4. What it outputs. A verdict (valid, invalid or unknown), a list of anomalies with evidence, a history file, a timeline and statistics. Examples of statistics are the anomaly rate with a confidence interval, and pass^k.
  5. Does it exist already? Only in parts. MCP chaos tools, the official MCP conformance suite, LLM fault injection (AgentChaos) and formal work on multi-agent concurrency exist. A proposal to add idempotency keys to MCP (SEP-3182) closed without a merge. No public tool joins faults, unknown results, a checker and published analyses.
  6. Talk and demo. Use a title like "Call Me Maybe, Agent". Show a live payment agent. Under a dropped connection, it reports "paid once" but pays two times. Then apply the fix and show a clean result with an honest statistical bound.
02
Foundations

What Jepsen is and how it works

Jepsen is a method and an open-source tool to test distributed systems. Kyle Kingsbury started it in 2013 with the blog series "Call Me Maybe". His company, Jepsen LLC, now publishes the analyses. Each analysis tests what a vendor claims. Then it tries to break that claim with faults.

2.1 The idea in one paragraph

A database vendor says: "Your data is safe, even if the network fails." Jepsen does not read the code to check this claim. It installs the real database on several nodes. Many clients send operations at the same time. A process called the nemesis injects faults: it cuts the network, kills processes, pauses them and changes clocks. Jepsen records every operation and every result in a history. At the end, a checker examines the full history. It searches for a result that no correct database can give. If it finds one, that history is a counterexample: proof of a bug.

  • 01Opaque-box testing. Jepsen tests real binaries through their public APIs. It does not need the source code.
  • 02Generative testing. Random operations from many clients make rare timing problems occur often.
  • 03Realistic faults. Partitions, crashes, pauses and clock skew occur in production. Jepsen causes them on purpose, on a schedule.
  • 04An honest limit. Jepsen says it plainly: "we cannot prove correctness, only find errors."Source: jepsen.io/analyses
Note · checked 5 October 2026

Recent analyses include TigerBeetle 0.16.11 (June 2025), Amazon RDS for PostgreSQL 17.4 (April 2025), NATS 2.12.1 (December 2025) and MariaDB Galera Cluster 12.1.2 (March 2026). The analyses page lists no AI agent, LLM or MCP system.

2.2 The parts of a test

Click a fault. The diagram shows what the nemesis does to the cluster. The text below the diagram tells you what can go wrong.

Generator
Makes a stream of random operations, for example "write 3" or "read". It also sets how many clients run at the same time.
Client
Sends each operation to a node. It records the start (invoke) and the result (ok, fail or info).
Nemesis
A special client that injects faults on a schedule: partitions, crashes, pauses and clock changes.
History
The ordered list of all invokes and results from all clients. It is the only evidence that the checker uses.
Model
A small definition of correct behavior, for example "one register" or "a queue".
Checker
Searches the history for behavior that the model does not allow. It reports valid, invalid or unknown.

How one test run works

  1. Install the system on five nodes. Use the real binaries.
  2. Start the clients and the nemesis.
  3. Run random operations for a fixed time, for example 10 minutes.
  4. Inject faults and remove them again during the run.
  5. Remove all faults. Let the system recover. Do final reads.
  6. Give the full history to the checkers.
  7. Write the verdict, the history and the graphs to the store directory.

Important

A timeout is not a failure. The operation can still take effect later. If a test records a timeout as fail, the checker can report false bugs or miss real bugs. Jepsen records it as info. This rule is the most important idea to bring to agents.

Quick check

A test client sends pay invoice 42. The connection times out before a response arrives. What must the test record?

2.4 How the checker decides

The checker uses a model of correct behavior. Think of one register: one value that clients write and read. The strongest model for a register is linearizability. Each operation must seem to take effect at one moment, inside its bar. Try to put one point inside each bar. Each read must then return the value of the last write before it. If such points exist, the history is valid. If no set of points works, the history is invalid.

  • An ok operation takes effect exactly one time, inside its bar.
  • A fail operation never takes effect.
  • An info operation takes effect one time or not at all. Its point can be at any time after its start.

W = write, R = read. A dashed bar with a fade has an unknown result (info).

Puzzle 1

Is this history linearizable? The register starts at 0.

The checker in this page searches all orders. Real checkers do the same search for histories with many thousands of operations. Knossos checks linearizability. Elle checks transaction isolation with dependency graphs. Checking linearizability is NP-complete in general, so these tools use smart search and special workloads.

03
The bridge

Why agents have the same problem

An agent that calls tools through MCP is a distributed system. Like a database cluster, it has clients, a network, servers and state. So it has the same failure modes. The LLM adds new ones, because it decides when to retry and it writes the final report.

3.1 Six facts from the MCP specification (2026-07-28)

  • 01MCP is stateless. Version 2026-07-28 removes protocol sessions and the Mcp-Session-Id header. Each request carries its protocol version and the client capabilities in _meta.Source: MCP changelog
  • 02A broken stream loses the request. Stream resumption with Last-Event-ID is removed. If the response stream breaks, the request is lost. To get a result, the client must send it again as a new request with a new ID.Source: Streamable HTTP transport
  • 03A disconnect is a cancellation. On Streamable HTTP, the server must treat a closed response stream as a cancel. On stdio, the client sends notifications/cancelled. A cancel can arrive after the work is complete.Source: Cancellation
  • 04Tool annotations are only hints. idempotentHint is false by default and destructiveHint is true by default. Clients must treat annotations as untrusted unless the server is trusted.Source: Tools
  • 05requestState is not single-use. In the new multi-round-trip pattern (MRTR), the server must integrity-protect requestState if it affects business logic. The specification says that this does not guarantee single use. A server that needs at-most-once behavior must enforce it.Source: MRTR pattern
  • 06There is no idempotency key. SEP-3182 proposed an idempotencyKey for tools/call. It says that a client "has no safe way" to retry a side-effecting call after a dropped connection, and calls this "an acknowledged gap". The pull request closed without a merge.Source: PR #3182

Important

The protocol cannot prevent this double payment. MCP has no idempotency key, and tool annotations are only hints. Only the two ends can make the effect occur one time: the server with a deduplication table, and the agent harness with a stable key.

Note · the end-to-end argument

Saltzer, Reed and Clark described this in 1984. A lower layer cannot give a correct end result alone. The end points must check it. In an agent system, the end points are the agent harness and the tool server, with its database.

3.3 What the LLM adds

  • The LLM decides to retry. It can change the arguments, for example the amount or the key.
  • The LLM writes the final report. It can claim success after an unknown result.
  • Errors arrive as text. The LLM can misread them, or follow instructions inside them.
  • Many agents can share one tool server and one state. Their reads and writes can interleave.
  • Tool lists can change during a run. The LLM can use an old tool description.

07
What to check

Properties and anomalies

A property is a rule that every history must obey. Jepsen-style tests use two kinds of properties. An anomaly is a pattern in a history that breaks a property.

Safety Nothing bad happens

Examples: an invoice is paid at most one time. No effect occurs without approval. The final claim matches the world.

One counterexample proves a violation.

Liveness Something good happens eventually

Examples: after the faults stop, the task completes. Retries stop after a limit.

A finite test cannot prove a violation. Use a time limit as a practical rule.

7.1 Proposed anomaly names for agents

Our proposal

These names are a proposal for this guide. They are not a standard. The paper arXiv 2606.17182 uses other names (stale-generation, phantom-tool, causal-cascade, tool-effect reordering) for related multi-agent problems.

A1Duplicate Effect
Definition
One requested effect occurs two or more times.
Example
Two payment rows for invoice #42.
Detect
Count the effects for each intent in the world state. A count above 1 is a violation.
Cause
A retry after an unknown result, with no idempotency key.
A2False Success
Definition
The agent reports a success that the world does not show. The effect is missing, or it differs from the claim.
Example
"Paid." The ledger has no row. Or: "Paid once." The ledger has two rows.
Detect
Compare the structured claim of the agent with the world state.
Cause
The agent guesses after an unknown result.
A3Hidden Effect
Definition
An effect occurred, but the agent reports a failure or does not report it.
Example
"The payment failed. Please try again." The ledger has a row.
Detect
Find effects in the world that no claim explains.
Cause
The agent treats an unknown result as a failure.
A4Unapproved Effect
Definition
An effect occurs without the necessary approval, or outside the scope of the task.
Example
A refund that the user did not ask for, after a prompt injection. Or a replayed requestState that approves a second action.
Detect
Match each effect to an approved intent.
Cause
Prompt injection, replay, or trust in hints.
A5Lost Update
Definition
Two agents read the same value and write updates based on it. One update is lost.
Example
Two agents book the last seat. Both get a success.
Detect
An invariant (bookings ≤ seats), or Elle on read/write histories.
Cause
Read, think, then write, with no lock or compare-and-set.
A6Stale Tool View
Definition
The agent acts on an old tool list, schema or resource.
Example
It calls a tool that the server removed or changed.
Detect
Compare the tool version in each call with the server version at that time.
Cause
Cached lists after ttlMs, or a missed list-changed notification.
A7Hint Violation
Definition
A tool behaves against its annotations.
Example
readOnlyHint is true, but the tool writes to the database. Or idempotentHint is true, but a repeated call makes a second effect.
Detect
Call the tool. Then compare the world state before and after.
Cause
Wrong or malicious annotations.
A8Retry Storm (liveness)
Definition
The agent retries with no end, or it makes no progress after the faults stop.
Example
40 calls in 10 seconds after a token expires.
Detect
Count the calls for each intent. Measure the time to completion after the faults stop.
Cause
No backoff and no retry limit.
A correct outcome: Honest Unknown

Sometimes the agent cannot know the result. Then the correct answer is: "I do not know if the payment went through. Please check before you try again." This is like a database that refuses requests during a partition. It is safe, but it is not live. The checker counts it separately, not as an anomaly.

7.2 How to prevent each anomaly

AnomalyPrevention
A1 Duplicate EffectThe harness owns an idempotency key for each intent. The server stores the key in the same transaction as the effect.
A2 False SuccessBuild the final claim from tool results, not from free text. Report "unknown" when the result is unknown.
A3 Hidden EffectReport "unknown" instead of "failed". Check the status before the final report.
A4 Unapproved EffectBind approvals to one action. Make requestState single-use on the server. Treat tool results as data, not as instructions.
A5 Lost UpdateUse atomic operations or compare-and-set on the server.
A6 Stale Tool ViewObey ttlMs. Refresh the list after a change notification. Put versions on tool schemas.
A7 Hint ViolationDo not trust hints from untrusted servers. Test the hints.
A8 Retry StormSet a retry limit. Use exponential backoff with jitter. Add a circuit breaker.

    Evidence

    What a Jepsen-style test proves, and what it does not

    A test gives two kinds of results. A failure is a proof. A pass is only evidence. Keep the two apart in every slide and in every report.

    Proves

    • A bug exists, if the checker finds one counterexample.
    • The bug can occur with legal protocol behavior and realistic faults.
    • Which layer must change: the harness, the server or the protocol.
    • A claim is false, for example "safe to retry" or "read-only".

    Does not prove

    • That the system is correct. A clean result only gives a bound.
    • That faults, prompts or models that you did not test are safe.
    • That the rate from a small workload is the rate in production.
    • That the LLM is the cause. Research shows that the system design is often more important.

    Measures

    • The anomaly rate for each fault and policy, with a confidence interval.
    • pass^k: the chance that k runs in a row are all valid.
    • The effect of a fix: before and after, with the same seeds.
    • Liveness: the time to recover after the faults stop.

    AgentChaos (ASE 2026) injected crash, omission and value faults into LLM API calls, in 65 configurations. Task success (pass@1) dropped by up to 50 points. The robustness ranking of the systems stayed the same across models. This suggests that robustness depends more on the system design than on the model. Automatic diagnosis of the faults stayed below 56% accuracy.

    What the test outputs, and how

    A Jepsen-style test for agents produces files, not only a score. Each file has one job. Together, they let another person repeat and check your result.

    Run

    The runner starts the server, the proxy and the agents. It runs the generator and the nemesis.

    config.json

    Record

    Each layer writes events with the same trace ID.

    history.jsonlnemesis.jsonleffects.jsonltranscript.jsonl

    Check

    The checker reads the history and the final world state. It applies the rules of the model.

    world.jsonresults.json

    Report

    The reporter makes a time line, a summary table and an exit code.

    timeline.htmlsummary.csv

    Procedure: from run to report

    1. Start the MCP server, the fault proxy and the world database in a clean state.
    2. Start the agents. Give each agent one task from the generator.
    3. Start the nemesis. Let it inject faults on a schedule.
    4. Record each invoke and each result (ok, fail or info) in history.jsonl.
    5. Record each real side effect in effects.jsonl. Get it from the server or the database, not from the agent.
    6. Stop the faults. Wait until the system is stable. Read the final world state.
    7. Run the checker on the history, the effects, the world state and the agent claims.
    8. Write results.json and timeline.html. Set the exit code.

    13.2 Abstract

    Your agent says "Done." Is it true? Agents call tools over MCP, and networks fail. A response stream breaks after the server commits a payment. The client sends the call again. The agent reports "paid once", but the ledger shows two payments. In databases, Jepsen made such bugs visible: inject faults, record every operation with honest "unknown" results, and check the history against a model. This talk applies the Jepsen method to MCP servers and AI agents. I show a small open-source harness. It injects faults, records one history across the agent, the protocol and the world, and checks it for anomalies such as duplicate effects and false success claims. You will see a live double payment, the fix (harness-owned idempotency keys, server deduplication and honest unknowns), and a clean result with an honest statistical bound. You will leave with a test method, a list of anomalies, and a checklist for your own tools.

    13.3 Three takeaways

    1. A timeout is not a failure. Treat it as unknown: in the agent, in the harness and in the test.
    2. Exactly-once effects need the ends. Use a stable key from the harness and deduplication in the server. The protocol alone cannot do it.
    3. Test the claim, not only the call. Compare what the agent says with what the world shows.

    13.5 Questions to prepare for

    "Is this a real Jepsen analysis?"

    No. It uses the Jepsen method. Jepsen is the work and the company of Kyle Kingsbury. Say "Jepsen-style" and give credit to the original work.

    "LLMs are random. How can a test be repeatable?"

    Fix the seeds where possible. Record the full transcripts. Report rates with confidence intervals. One counterexample is still proof of a bug, and you can replay it from the recorded transcript.

    "Is this not just chaos engineering?"

    Chaos engineering checks that a system stays healthy. A Jepsen-style test checks a formal property on the full history, with unknown results. A checker decides, not a dashboard.

    "Why not fix it in the protocol?"

    The end-to-end argument says that the ends must check. A protocol key helps, but the server must still deduplicate and the harness must still reuse the key. SEP-3182 proposed such a key. It closed without a merge.

    "Does temperature 0 fix it?"

    No. The bug is in the retry logic and in the server, not in the randomness of the model. Temperature 0 only makes the bug easier to repeat.

    "What about read-only tools?"

    They are safe to retry if they are really read-only. Test that with A7 (Hint Violation). Annotations are hints, and clients must not trust them by default.

    "How expensive is this?"

    Level 1 needs no model calls. A Level 2 batch of 100 runs with about 5 calls each is 500 model calls. Use a small model for volume and cache responses for the demo.

    Naming and ethics

    Say "Jepsen-style" or "inspired by Jepsen". Do not call your work "a Jepsen analysis". Jepsen LLC has no connection to this work unless it says so. If you find a bug in a real project, tell the maintainers first. Give them time to fix it before the talk.

    Remove the key field from the tool schema that the LLM sees. Add the key in the harness. Then the LLM cannot change it or forget it. Also ask the agent for a structured claim, for example {status, invoice, amount, payments}. The checker can then verify it exactly.

    server.py · deduplication in the same transaction as the effect
    # Sketch. The key and the effect commit together, or not at all.
import json, sqlite3
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("ledger")
db = sqlite3.connect("world.db", isolation_level=None)

@mcp.tool()
def pay_invoice(invoice: int, amount: int, idempotency_key: str) -> dict:
    db.execute("BEGIN IMMEDIATE")
    try:
        row = db.execute("SELECT result FROM dedupe WHERE key = ?",
                         (idempotency_key,)).fetchone()
        if row:                                   # a repeat: no new effect
            db.execute("COMMIT")
            return json.loads(row[0])
        db.execute("INSERT INTO payments(invoice, amount) VALUES (?, ?)",
                   (invoice, amount))
        result = {"status": "paid", "invoice": invoice, "amount": amount}
        db.execute("INSERT INTO dedupe(key, result) VALUES (?, ?)",
                   (idempotency_key, json.dumps(result)))
        db.execute("COMMIT")
        return result
    except Exception:
        db.execute("ROLLBACK")
        raise
    harness.py · the LLM never sees or writes the key
    # Sketch. One key per intent. Unknown results stay unknown.
import uuid

class Harness:
    def __init__(self, session, recorder):
        self.session = session          # an MCP client session
        self.record = recorder          # writes history.jsonl
        self.keys = {}

    def schema_for_llm(self, tool):
        s = dict(tool.inputSchema)
        s["properties"] = {k: v for k, v in s["properties"].items()
                           if k != "idempotency_key"}
        s["required"] = [r for r in s.get("required", []) if r != "idempotency_key"]
        return s

    async def call(self, task_id, name, args):
        intent = (task_id, name, args.get("invoice"))
        key = self.keys.setdefault(intent, str(uuid.uuid4()))
        self.record("invoke", task_id, name, args, key)
        try:
            result = await self.session.call_tool(name, {**args, "idempotency_key": key})
        except (TimeoutError, ConnectionError) as e:
            self.record("info", task_id, name, args, key, error=str(e))
            raise                       # unknown, not failed
        # isError is a fail only if the server promises "no effect"
        self.record("fail" if result.isError else "ok", task_id, name, args, key)
        return result
    proxy.py · drop the result after the server commits
    # Sketch, not production code. It buffers the full response.
import random
from aiohttp import web, ClientSession

UPSTREAM = "http://127.0.0.1:9000/mcp"
P_DROP_AFTER_COMMIT = 0.15

async def handle(request):
    body = await request.read()
    async with ClientSession() as s:
        async with s.post(UPSTREAM, data=body, headers=pass_headers(request.headers)) as up:
            data = await up.read()       # the server is done: the effect exists
            if random.random() < P_DROP_AFTER_COMMIT:
                log_fault("drop-after-commit", body)
                request.transport.close()   # break the stream: no result arrives
                return web.Response(status=502)
            return web.Response(body=data, status=up.status,
                                headers=pass_headers(up.headers))

app = web.Application()
app.router.add_post("/mcp", handle)
web.run_app(app, port=8080)
    checker.py · rules A1–A3
    # Sketch. Trust the effects log and the claims, not the transcript.
import json
from collections import Counter

def load(path):
    with open(path) as f:
        return [json.loads(line) for line in f]

def check(effects_path, claims_path):
    paid = Counter(e["invoice"] for e in load(effects_path) if e["kind"] == "payment")
    anomalies = []
    for c in load(claims_path):              # one structured claim per task
        n = paid.get(c["invoice"], 0)
        if n > 1:
            anomalies.append({"type": "A1", "task": c["task"], "payments": n})
        if c["status"] == "paid" and n != 1:
            anomalies.append({"type": "A2", "task": c["task"], "payments": n})
        if c["status"] == "failed" and n >= 1:
            anomalies.append({"type": "A3", "task": c["task"], "payments": n})
    return {"valid": not anomalies, "anomalies": anomalies}

    Glossary

    Agent harness
    The code around an LLM. It runs the loop, calls the tools and records the events.
    Anomaly
    A pattern in a history that breaks a property. Example: two payments for one request.
    Checker
    Code that reads a history and decides if it is valid.
    Clock skew
    A difference between the clocks of two computers.
    Counterexample
    One history that breaks a property. It proves that a bug exists.
    Elle
    A Jepsen checker for transaction isolation. It finds anomalies with dependency graphs.
    End-to-end argument
    A design principle: only the end points of a system can guarantee a correct result.
    Generator
    Code that makes the operations for a test.
    History
    The full, ordered record of operations and results in a test.
    Idempotent
    An operation is idempotent if two or more executions have the same effect as one execution.
    Idempotency key
    A unique ID that the client attaches to a request. The server uses it to find repeats.
    info (result)
    A result type that means "unknown". The operation took effect one time or not at all.
    Linearizable
    A consistency model. Each operation seems to occur at one moment between its start and its end.
    Liveness property
    A property that says that something good must occur eventually.
    MCP (Model Context Protocol)
    An open protocol that connects AI applications to tools and data.
    MRTR
    The multi-round-trip request pattern in MCP 2026-07-28. The server asks for input. The client sends the request again with the answers and the requestState.
    Nemesis
    The part of a Jepsen test that injects faults.
    Opaque-box testing
    Testing a system only through its public interface.
    Partition
    A network fault that divides the nodes into groups that cannot communicate.
    pass^k
    The chance that k independent attempts at the same task all succeed.
    Rule of three
    If you see 0 failures in N independent attempts, the 95% upper bound on the failure rate is about 3/N.
    Safety property
    A property that says that something bad must never occur.
    Side effect
    A change in the world outside the conversation, for example a payment or an email.
    Wilson interval
    A method to calculate a confidence interval for a rate. It works well for small counts.
